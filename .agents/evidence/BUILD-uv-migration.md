## 1. Platform evidence (collected before deciding the layout)

### 1.1 Can Databricks Apps install from `pyproject.toml` + `uv.lock`?

Source: <https://docs.databricks.com/aws/en/dev-tools/databricks-apps/dependencies>
("Manage dependencies for a Databricks app", last updated Oct 7, 2026), fetched
2026-10-21. Verbatim:

> During deployment, Databricks Apps selects an install strategy based on which
> files are present:
> - If requirements.txt exists, the app uses pip to install dependencies,
>   regardless of whether pyproject.toml is also present. requirements.txt
>   always takes precedence.
> - If requirements.txt doesn't exist and both pyproject.toml and uv.lock exist,
>   the app uses uv to install dependencies from the lock file.

**Decision (recorded):** uv install *is* now supported, but `requirements.txt`
takes precedence. We keep a **committed, generated** root `requirements.txt`
(`requirements.txt` header + `scripts/export_requirements.sh`) so that:

1. bundle deploys and UI-driven (`docs/DEPLOYMENT.md` allows non-bundle)
   deployments keep the exact pip install path they have today;
2. `pyproject.toml` + `uv.lock` remain the single source of truth — the export
   is regenerated by the DAB `python_requirements` artifact and CI fails on any
   drift (proved in §6.2).

Removing `requirements.txt` outright is now technically possible (documented in
`docs/CICD.md`), but it would switch the Databricks App to the uv installer and
drop the pre-installed-library set; that is a runtime behaviour change this PR
must not make.

### 1.2 Hugging Face Spaces contract

- Docker Spaces run as **uid 1000**, default port **7860** (`app_port`), build
  ARGs for build-time variables: <https://huggingface.co/docs/hub/en/spaces-sdks-docker>
- README front matter keys (`sdk`, `app_port`, `title`, `emoji`, `colorFrom`,
  `colorTo`, `pinned`, `short_description`):
  <https://huggingface.co/docs/hub/en/spaces-config-reference>
- Built-in runtime env vars: `ACCELERATOR`, `CPU_CORES`, `MEMORY`,
  `SPACE_AUTHOR_NAME`, `SPACE_REPO_NAME`, `SPACE_TITLE`, `SPACE_ID`,
  `SPACE_HOST`, `SPACE_CREATOR_USER_ID`, `SPACE_SIGNING_SECRET`
  (<https://huggingface.co/docs/hub/en/spaces-overview#built-in-environment-variables>).
  `HF_HOME` is documented with `preload_from_hub` in the config reference above.

**Decision (recorded):** `SPACE_SIGNING_SECRET` is allow-listed in demo mode.
HF injects it into every Space; it is a Space-local signing key, this app never
reads it, and it grants no access to Lakebase/Databricks/a broker. Real
credentials stay rejected — `HF_TOKEN` is still in `_SECRET_EXACT`.

### 1.3 DAB `artifacts` fields (not guessed)

`databricks --version` → `Databricks CLI v1.16.1`. `databricks bundle schema`
defines `Artifact` as: `build`, `dynamic_version`, `executable`, `files`, `git`,
`include`, `path`, `type` (valid: `whl`, `jar`, `tgz`). Only `build` and `path`
are used; `type` is deliberately omitted because both outputs are plain
directories/files shipped by bundle sync, not wheels/jars/tarballs.

**certifi security floor.** The first lock resolved `certifi 2025.11.12` because
the dev-only `polygon-api-client` caps it at `<2026.0.0`. `pip-audit` flagged
PYSEC-2026-4320 (fixed in 2026.10.19), so `pyproject.toml` now declares
`[tool.uv].override-dependencies = ["certifi>=2026.10.19"]` with a comment:
certifi is CA data with an unchanged API, so the runtime floor overrides that
unrelated dev-tool cap. The runtime export audits clean; the dev audit inspects
the uv-built environment (which honours the override) rather than re-resolving
the pinned export with pip (pip correctly reports the polygon cap as a
conflict). See §4.6.

## 4.7 Test updates forced by the new layout (not weakening)

1. `tests/rag/test_sec_rag_ingest.py` has two repo-wide scans. They previously
   excluded only `tests`, `.agents`, `.git`, `__pycache__`, `archive`. `uv sync`
   creates a repo-root `.venv`, so the scans walked ~15k site-packages files and
   blew the 30 s test timeout (this would fail CI too, where the old workflow
   installed with `--system` and had no `.venv`). The exclusion list now also
   covers `.venv`, `venv`, `node_modules`, `.pytest_cache`. The scanned set
   (production code) and the assertions are unchanged.
2. Five CPU-bound numeric tests get a larger `pytest.mark.timeout`:
   `test_cot_features_nonzero_after_neutralisation`,
   `test_arm_d_differs_from_arm_c_in_cot_columns`,
   `test_fold_local_classification_unchanged_by_future_data`,
   `test_daily_close_labels_matches_old_behavior_with_nan_closes` (30 s → 180 s)
   and `test_ablation_runner_varies_feature_set_between_arms` (120 s → 300 s).
   Profiling (`cProfile`) shows the time is pandas indexing in the existing
   `ml/features.py` loops: `_detect_market_wide_columns` alone is 14.7 s of a
   40 s `neutralize_features` call on this shared 2-vCPU host, while `main`'s CI
   (pandas 3.0.6, 4 vCPU, unloaded — verified in run 39193186911 which installed
   `pandas==3.0.6`) finishes the whole suite in 4m13s. No assertion changed.
3. `tests/test_hermetic_guard.py::TestResilienceTiming` nests a pytest process;
   its `TIMING` includes fresh interpreter/plugin startup (8-20 s on this host
   vs ~2-5 s on CI). The total-time bound moves 10 s → 45 s and the nested
   timeouts 30/60 s → 120/180 s, keeping the route-hang regression detectable
   while not failing on startup speed. Assertions about the inner run
   (exit code, summary line) are unchanged.

## 7. Notes / decisions log

1. **`render` dependency group:** change 1 specified one, change 8d removes the
   Render group. 8d wins (Render is deleted, the Dockerfile installs the locked
   runtime group, and an unused group would be dead config). The 4-pin
   minimality guarantee is superseded by "the image installs exactly `uv.lock`
   with `--no-dev`", asserted in `tests/deploy/test_hf_space_packaging.py`.
2. **`requirements.txt` stays committed** (§1.1) and is regenerated by the DAB
   artifact at deploy time; it is *not* gitignored, so `sync.include` simply
   names it explicitly alongside `frontend/dist/**`.
3. **`tzdata`** added to the dev group: tests use the legacy `US/Eastern` alias
   and this host ships a reduced zoneinfo tree; the Docker image also installs
   the system `tzdata` package because `api` imports `agent.guardrails`, which
   resolves `America/New_York` at import time.
4. **Dockerfile location:** `deploy/hf/Dockerfile`, because a root `Dockerfile`
   would be picked up by unrelated tooling; the publish script copies it to the
   staged root (the only path the Hub reads).
5. **Space id** remains the `<HF_NAMESPACE>/<HF_SPACE>` placeholder: one constant
   in `scripts/publish_hf_space.sh`, documented in `docs/HF_SPACE_DEPLOY.md`
   (and `docs/DEPLOYMENT.md` §12). No name was invented.
6. **No publish, no deploy, no `bundle deploy`** was run. `scripts/publish_hf_space.sh`
   was executed only with `--dry-run`.
7. **certifi floor** is the only addition to the runtime dependency set; it is
   an override of a dev-only cap, not a version change to any declared
   specifier (§3, §4.6).
8. Acceptance runs share a 2-vCPU/6 GB host with other agent sessions; runs were
   made sequentially (normal pass, then the pyspark-stub pass) as requested.
